# Memora 文档与问答可观测性建设计划

## 1. 背景与结论

Memora 面向个人用户，不需要按“管理员”和“普通用户”划分可观测能力。信息应按使用场景和深度分层：正常使用时保持简洁，出现异常或用户主动查看时再展开技术细节。

本次建设分为两个相互独立、但共享底层关联标识和观测规范的产品面：

1. **文档可观测性**：放在知识库中，回答“文档是否已经可检索、当前处理到哪一步、失败后如何恢复”。
2. **问答可观测性**：升级现有“运行记录”，回答“这次回答经过了哪些步骤、使用了哪些知识和工具、为什么慢或失败”。

不新增统一的“可观测性首页”，也不把文档处理、问答链路和基础设施状态混在一个页面中。

## 2. 建设目标

### 2.1 文档可观测性

- 用户能够确认知识库中的文档是否已经进入可检索状态。
- 用户能够看到处理中和失败的文档，并执行重试或重新索引。
- 用户能够查看单个文档的处理阶段、阶段状态、失败原因和关键耗时。
- 系统能够识别任务停滞，而不只是显示数据库中的静态状态。

### 2.2 问答可观测性

- 用户能够从运行记录或聊天回答进入一次完整的问答运行详情。
- 用户能够看到查询处理、检索、重排、上下文构造、模型生成和工具调用的结果摘要。
- 用户能够理解回答引用了哪些文档，以及没有得到答案时发生了什么。
- 系统能够用统一的运行标识关联页面、日志、错误和底层 Trace。

### 2.3 非目标

- 不展示模型的完整思维链。
- 不默认保存或展示完整 Prompt、文档正文、工具敏感参数和模型完整上下文。
- 不在普通页面中常驻展示 Redis、PostgreSQL、Worker 等基础设施面板。
- 本阶段不建设独立的大型监控中心或替换现有聊天、知识库页面。

## 3. 产品信息架构

```text
知识库
├── 文档列表
│   ├── 可检索
│   ├── 处理中
│   └── 失败
└── 文档详情
    └── 上传 → 解析 → 分块 → 向量化 → 索引

对话
└── 回答
    ├── 查看依据
    └── 查看运行详情 → /runs/{runId}

运行记录
├── 问答运行列表
└── 问答运行详情
    └── 查询 → 检索 → 重排 → 模型 → 工具 → 回答

设置
└── 诊断信息（后续可选）
```

### 3.1 文档页面展示原则

知识库和文档列表只展示用户可以理解和处理的信息：

- 文档总数、可检索数量、处理中数量、失败数量。
- 当前状态和最近更新时间。
- 失败原因摘要。
- “重试处理”和“重新索引”操作。

正常文档不默认展开完整流水线。用户打开文档详情或点击失败状态后，再显示：

```text
上传 ✓ → 解析 ✓ → 分块 ✓ → 向量化 ✗ → 索引
```

### 3.2 运行记录展示原则

保留现有 `/runs/:runId?` 路由和“运行记录”导航，不再新增重复标签。现有页面改造成正式的问答可观测入口。

列表展示：

- 用户问题摘要。
- 使用的知识库和会话。
- 运行状态。
- 总耗时。
- 执行模式。
- 创建时间。

详情展示：

- 问题、回答摘要、知识库和模型。
- 总耗时、首字延迟、输入/输出 Token。
- 查询处理、关键词检索、向量检索、融合、重排、知识充分性判断和模型生成。
- Tool/MCP 调用结果摘要。
- 命中文档、引用片段和最终引用。
- 错误阶段、错误码、用户可理解的原因与恢复建议。

聊天页中的内联链路继续保留，但收敛为简要状态、引用和“查看完整运行详情”入口。

## 4. 现有能力与复用策略

### 4.1 文档侧现状

现有能力包括：

- `import_tasks` 已包含状态、执行次数、当前步骤、失败原因和开始/完成时间。
- `document_previews` 已包含预览状态、渲染器、执行次数、错误和时间字段。
- 文档实体和处理接口已经提供处理状态、失败步骤、索引模式与索引版本。
- 前端 `DocumentProcessingPanel` 已支持查看文档状态、失败重试和重新索引。

因此文档可观测性以整合和补全为主，不从零重建。

### 4.2 问答侧现状

现有能力包括：

- `/runs/:runId?` 已提供运行列表与详情入口。
- `agent_runs` 已保存问题、模式、知识充分性、执行轨迹摘要、Token、耗时、结果和错误。
- `agent_events` 已支持中间事件持久化、SSE 推送和断线回放。
- `tool_calls` 已保存工具调用元数据和输入输出摘要。
- 聊天页面已经使用 `InlineAgentRun` 展示实时与历史运行过程。

因此问答可观测性是对现有“运行记录”的结构化升级，不建设第二套运行数据。

## 5. 统一观测数据规范

两类可观测性使用统一的关联与阶段规范，但分别存储和展示。

### 5.1 关联字段

- `trace_id`：一次跨服务执行的 W3C Trace ID。
- `request_id`：触发任务或运行的 HTTP 请求 ID。
- `run_id`：问答或 Agent 运行 ID。
- `task_id`：文档导入、预览或索引任务 ID。
- `document_id`、`knowledge_base_id`：业务归属。

日志、事件和错误响应应尽量携带上述适用字段，支持从页面记录定位日志和 Trace。

### 5.2 阶段事件通用字段

```text
stage
status: pending | running | succeeded | failed | skipped
started_at
ended_at
duration_ms
error_code
error_message
summary
metadata（经过白名单与脱敏）
```

### 5.3 文档阶段

```text
upload
parse
normalize
chunk
embed
index
preview（独立派生流程）
```

### 5.4 问答阶段

```text
route
query_rewrite
keyword_retrieve
vector_retrieve
fusion
rerank
knowledge_check
context_build
model_generate
tool_call
answer
```

阶段允许跳过或降级，但必须明确记录 `skipped` 或降级原因，不能通过缺失事件表达。

## 6. 后端实施计划

### 6.1 文档可观测后端

#### P0：复用现有状态完成最小可用版本

- 统一 `import_tasks.current_step`、文档 `processing_status/failure_step` 和索引版本的状态映射。
- 提供知识库级处理状态汇总：总数、可检索、处理中、失败。
- 保持现有单文档处理状态接口，补齐用户可理解的错误码和恢复建议。
- 让重试操作返回新的任务标识，并在 UI 中立即进入处理中状态。

#### P1：补充阶段历史

新增追加式文档处理事件表，建议命名为 `document_processing_events`：

```text
id
knowledge_base_id
document_id
task_id
stage
status
started_at
ended_at
duration_ms
attempt
error_code
error_message
metadata
created_at
```

每个阶段开始与结束时写入事件。事件写入失败不得阻塞文档主流程，但必须记录结构化错误并增加失败指标。

#### P1：真实任务健康指标

- 文档任务数量：按 `job_type/result`。
- 处理时长：按阶段记录 Histogram。
- 队列等待时间。
- 最老待处理任务年龄。
- 重试次数和失败原因类别。
- Worker 最后心跳。
- Redis Stream pending 和 Outbox backlog。

修正当前 Worker 健康检查，不再用配置并发数代表真实运行状态。

### 6.2 问答可观测后端

#### P0：规范现有运行事件

- 统一现有 Router、ReAct、Tool、Citation 和 Answer 事件结构。
- 为检索、融合、重排、知识充分性和模型生成补充明确阶段事件。
- 每个阶段记录开始、结束、状态和耗时。
- 失败事件记录稳定错误码、失败阶段和可恢复性。

#### P0：补充用户关心的摘要

- 检索结果数量和最终引用数量。
- 命中文档 ID、标题与安全的片段摘要。
- 模型标识、输入/输出 Token、首字延迟和生成耗时。
- Tool/MCP 名称、状态、耗时和脱敏结果摘要。
- 是否发生降级、重试或知识不足。

继续使用 `agent_runs`、`agent_events` 和 `tool_calls`，优先扩展现有 DTO/事件负载。只有现有 JSON 结构无法满足查询和索引要求时，才增加新表。

#### P1：接入标准 Trace

- 使用 OpenTelemetry SDK 建立真实 Span。
- 保留并传播现有 W3C `traceparent`。
- 在 Redis Stream producer/consumer、Go → Python Parser、模型请求和 MCP 请求间传播上下文。
- 将 `trace_id` 写入 `agent_runs` 和文档任务记录，建立产品记录与底层 Trace 的关联。

## 7. 前端实施计划

### 7.1 文档可观测前端

在现有知识库和文档工作区中渐进增强：

1. 知识库顶部增加轻量状态汇总。
2. 文档树和列表增加一致的状态标识。
3. 扩展 `DocumentProcessingPanel`，显示处理阶段、耗时、失败原因与建议操作。
4. 处理中状态使用轮询或现有事件机制更新，完成后停止轮询。
5. 失败文档提供重试；已成功且可检索的文档提供重新索引。
6. 预览生成作为独立派生状态展示，不把预览失败误报为文档不可检索。

### 7.2 问答可观测前端

改造现有运行记录：

1. 保留 `/runs` 列表和 `/runs/{runId}` 详情路由。
2. 将当前由一个页面同时承担的列表与详情拆成真正独立的页面组件，共享查询和展示组件。
3. 列表增加知识库、会话、状态、耗时和时间筛选，保留分页。
4. 详情按“摘要 → 引用 → 阶段时间线 → 工具调用 → 错误信息”组织。
5. 默认显示用户可理解的阶段名称；原始事件和 Trace ID 放在折叠的技术信息中。
6. 聊天页 `InlineAgentRun` 只展示实时进度、失败摘要、引用和跳转入口，避免与详情页重复。
7. 从运行详情中的引用文档跳回知识库文档；从文档详情可选跳转到引用该文档的运行记录。

## 8. 隐私与数据保留

### 8.1 默认不采集

- 完整 Prompt 和模型完整回复副本。
- 文档完整正文或大段原始切片。
- Tool/MCP 的认证信息和敏感参数。
- Authorization、Cookie、API Key。
- 不必要的用户标识、对象存储地址和原始 SQL 参数。

### 8.2 默认可采集

- 阶段名称、状态、耗时和错误码。
- 模型与工具名称。
- Token 数量。
- 文档 ID、标题和经过截断/脱敏的引用摘要。
- 低基数的任务、结果与错误类别。

### 8.3 配置建议

```yaml
observability:
  enabled: true
  capture_sensitive_content: false
  trace_sample_ratio: 1.0
  retention_days: 30
```

个人本地部署可以默认保留较高采样率，但仍应提供保留周期和一键清理能力。

## 9. 实施阶段与里程碑

### 阶段 A：契约与状态统一

- 定义文档和问答阶段枚举。
- 定义事件 DTO、错误码、脱敏字段白名单。
- 明确 `trace_id/request_id/run_id/task_id` 传播规则。

**验收：** 同一阶段在数据库、接口、日志和前端中使用相同名称与状态语义。

### 阶段 B：文档可观测 MVP

- 知识库状态汇总。
- 文档列表状态。
- 单文档处理链路。
- 失败原因、重试和重新索引。

**验收：** 用户无需查看日志即可定位失败文档、失败阶段并执行恢复操作。

### 阶段 C：问答运行记录升级

- 规范运行事件。
- 补齐检索、重排、模型与引用数据。
- 改版 `/runs` 列表和详情。
- 聊天页跳转完整运行详情。

**验收：** 用户能够解释一次回答使用了哪些知识、耗时主要发生在哪里，以及失败原因。

### 阶段 D：阶段历史与真实任务指标

- 文档处理事件历史。
- Worker 心跳、任务积压、等待时间和失败率。
- 任务停滞检测。

**验收：** Worker 卡死或任务不再流动时，系统能够被指标或状态检查发现。

### 阶段 E：OpenTelemetry 与底层诊断

- 接入 Go/Python OTel。
- 跨 HTTP、Redis、数据库、模型和 MCP 传播 Trace。
- 配置可选 Collector、Tempo/Jaeger 和 Prometheus/Grafana。

**验收：** 可以从运行记录的 Trace ID 定位完整跨服务调用链。

## 10. 测试计划

### 10.1 后端

- 阶段状态机和非法状态转换测试。
- 文档任务成功、失败、重试、停滞和取消测试。
- 问答运行成功、知识不足、检索降级、模型失败和工具失败测试。
- SSE 断线回放与事件顺序测试。
- `trace_id` 跨 HTTP、Redis 和 Python 服务传播测试。
- 脱敏规则和敏感字段禁止输出测试。
- Metrics 标签基数测试，禁止用户 ID、文档 ID 和 Run ID 进入指标标签。

### 10.2 前端

- 文档状态映射和阶段时间线组件测试。
- 失败重试、重新索引及状态刷新测试。
- 运行列表筛选、分页和详情深链测试。
- 实时事件与持久化详情一致性测试。
- 空状态、加载状态、长文本和错误状态测试。

### 10.3 端到端

1. 上传文档并观察其进入可检索状态。
2. 注入解析失败，确认失败阶段和重试入口。
3. 发起一次知识库问答，从聊天跳转运行详情。
4. 确认检索结果、引用和最终回答对应。
5. 注入模型或 MCP 失败，确认错误阶段与恢复建议。
6. 模拟 Worker 停止，确认任务停滞能够被发现。

## 11. 完成标准

- 文档可观测性只出现在知识库和文档上下文中。
- 问答可观测性由现有“运行记录”承载，不出现重复页面或重复数据源。
- 正常使用路径不暴露不必要的基础设施和技术细节。
- 所有失败状态都包含可理解原因；可恢复失败提供明确操作。
- 页面记录、结构化日志和底层 Trace 能通过统一标识关联。
- 默认配置不会采集或外发 Prompt、文档正文和凭据。
- 文档流程与问答流程均具备契约测试、前端测试和关键端到端测试。

## 12. 建议的开发顺序

1. 状态与事件契约。
2. 文档可观测 MVP。
3. 运行记录改版。
4. 文档阶段历史与任务指标。
5. OpenTelemetry 和可选外部观测栈。

这个顺序优先解决用户可见的状态与恢复问题，再建设跨服务技术诊断能力，避免在产品价值尚未验证前投入完整监控平台。
