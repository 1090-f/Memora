# Memora 模型绑定改造方案

## 1. 方案目标

根据 Memora 当前的知识库、Conversation、Agent Run、文档索引和模型配置实现，将三类模型按照实际生命周期重新划分：

| 模型类型 | 绑定对象 | 选择时机 | 修改规则 |
| --- | --- | --- | --- |
| Embedding Model | KnowledgeBase | 创建知识库时 | 创建后不可修改 |
| Chat Model | Conversation | 创建对话时 | 对话过程中可以切换 |
| Reranker Model | SearchConfig | 知识库创建后按需配置 | 可以修改或关闭 |

核心原则：

```text
Embedding = 索引级配置
Chat      = 会话运行时配置
Reranker  = 检索运行时配置
```

其中只有 Embedding 模型需要强不可变约束。

---

## 2. 核心字段定义

### 2.1 `KnowledgeBase.embedding_model_id`

表示当前知识库唯一确定的 Embedding 模型。

该模型决定文档向量和查询向量所在的语义空间，因此：

- 创建知识库时必须选择；
- 创建后不可修改或清空；
- 文档索引和向量检索不得回退到用户默认模型；
- 需要更换模型时，必须重新创建知识库并重新导入文档。

### 2.2 `Conversation.chat_model_id`

表示：

> **该 Conversation 后续创建 Run 时默认选择的 Chat 模型。**

该字段可以修改，但必须明确：

- 它只表示 Conversation 当前选择；
- 它不是历史模型记录；
- 它不能用于解释历史 Run 或历史 Assistant Message 使用了哪个模型；
- 切换后只影响后续新创建的 Run；
- 已经创建、排队或完成的 Run 不受影响。

### 2.3 `AgentRun.chat_model_id`

表示：

> **本次 Run 创建时确定的 Chat 模型身份引用。**

它是模型配置 ID 的引用快照，创建后不可修改。

除非系统同时复制并保存 Provider、`model_name`、Base URL 标识、Temperature、Max Tokens 等实际配置，否则不能把 `AgentRun.chat_model_id` 称为“完整配置快照”。

准确关系是：

```text
Conversation.chat_model_id
        ↓ Run 创建时重新校验并复制
AgentRun.chat_model_id
        ↓ Worker 执行时读取
AIModelConfig
```

如果未来需要严格还原历史执行环境，应另外保存 Run 级完整配置快照或关键参数快照。

### 2.4 `Message.model_config_id`

表示最终 Assistant Message 实际使用的模型配置 ID。

三个 Chat 模型字段的职责如下：

| 字段 | 含义 | 是否可变 |
| --- | --- | --- |
| `conversations.chat_model_id` | 后续 Run 默认选择的模型 | 可以修改 |
| `agent_runs.chat_model_id` | 本次 Run 的模型身份引用 | 创建后不可修改 |
| `messages.model_config_id` | 该条回复实际使用的模型 | 创建后不可修改 |

## 3. 当前项目现状

当前实现与目标方案存在以下差异：

1. 创建知识库时会调用 `resolveChatModel`，没有默认 Chat 模型就拒绝创建。
2. `agent_configs.chat_model_id` 当前是必填字段，因此知识库创建被迫依赖 Chat 模型。
3. `default_embedding_model_id` 当前允许为空，也允许通过知识库更新接口修改。
4. 知识库未配置 Embedding 时，文档处理和检索会回退到用户默认 Embedding 模型。
5. Chat 模型当前保存在 KnowledgeBase 和 AgentConfig，而不是 Conversation。
6. Conversation 创建接口当前只接收标题，没有 `chat_model_id`。
7. Agent Run 当前没有保存本次运行使用的 Chat 模型引用。
8. AgentContext 当前从 `agent_configs.chat_model_id` 读取 Chat 模型。
9. Reranker 同时存在于 KnowledgeBase 和 SearchConfig，形成两个数据来源。
10. 前端知识库创建页没有选择 Embedding 模型，知识库设置页仍允许修改 Chat 和 Embedding 模型。

本次改造需要统一消除以上差异。

## 4. 目标数据模型

### 4.1 KnowledgeBase

目标字段：

```text
knowledge_bases
--------------------------------
id
user_id
name
description
embedding_model_id NOT NULL
...
```

调整内容：

```text
default_embedding_model_id
    ↓ 重命名并改变语义
embedding_model_id

default_chat_model_id
    ↓ 删除
```

`embedding_model_id` 不再是默认值，而是知识库索引身份。

### 4.2 Conversation

新增：

```text
conversations.chat_model_id UUID NOT NULL
```

它保存后续 Run 默认选择的 Chat 模型，允许用户切换。

### 4.3 AgentRun

新增：

```text
agent_runs.chat_model_id UUID NOT NULL
```

它保存本次 Run 的模型身份引用，创建后不可修改。

### 4.4 Message

继续保留：

```text
messages.model_config_id
```

用于记录 Assistant Message 实际使用的模型配置。

### 4.5 AgentConfig

删除：

```text
agent_configs.chat_model_id
```

AgentConfig 只负责“如何执行”：

- System Prompt；
- ReAct 最大轮数；
- Plan-Execute 参数；
- 工具限制；
- 记忆配置；
- 联网开关；
- 执行状态展示。

使用哪个 Chat 模型由 Conversation 和 AgentRun 决定。

### 4.6 SearchConfig

Reranker 的唯一权威来源为：

```text
search_configs.reranker_model_id
```

删除：

```text
knowledge_bases.default_reranker_model_id
```

避免知识库表和检索配置表同时保存 Reranker。

## 5. 创建知识库流程

### 5.1 产品流程

```text
填写名称和描述
        ↓
选择 Embedding 模型
        ↓
确认创建后不可修改
        ↓
创建知识库
```

创建知识库不再要求用户提前配置 Chat 模型。

没有 Chat 模型时，用户仍然可以：

- 创建知识库；
- 导入和管理文档；
- 构建索引；
- 使用不依赖 Chat 的检索能力。

### 5.2 创建接口

```http
POST /api/v1/knowledge-bases
```

请求示例：

```json
{
  "name": "Go 后端学习资料",
  "description": "Go 服务端开发文档",
  "embedding_model_id": "embedding-config-id",
  "agent_enabled": true,
  "network_enabled": false
}
```

DTO：

```go
type CreateKnowledgeBaseRequest struct {
    Name             string  `json:"name" binding:"required,max=128"`
    Description      *string `json:"description" binding:"omitempty,max=2000"`
    EmbeddingModelID string  `json:"embedding_model_id" binding:"required"`

    AgentEnabled   *bool `json:"agent_enabled"`
    NetworkEnabled *bool `json:"network_enabled"`
}
```

后端校验：

- 模型存在；
- 模型属于当前用户；
- `model_type = embedding`；
- `enabled = true`；
- 模型名称、Base URL、向量维度等必要配置完整。

### 5.3 创建事务

```text
校验 Embedding 模型
        ↓
创建 KnowledgeBase
        ↓
创建默认目录
        ↓
创建 SearchConfig
        ↓
创建不依赖 Chat 模型的 AgentConfig
        ↓
提交事务
```

删除创建流程中的：

- `resolveChatModel`；
- 用户默认 Chat 模型查询；
- 因缺少 Chat 模型导致的创建失败。

## 6. KnowledgeBase 更新规则

`UpdateKnowledgeBaseRequest` 中不提供：

```text
embedding_model_id
default_embedding_model_id
default_chat_model_id
default_reranker_model_id
```

知识库更新接口只允许维护基础信息和普通功能配置。

Embedding 不可变约束必须由后端接口保证，不能只依赖前端禁用下拉框。

如果要求客户端提交 `embedding_model_id` 时明确返回参数错误，需要使用严格 JSON 解码。仅从 Go DTO 中删除字段时，Gin 默认可能忽略未知字段。

Reranker 统一通过 SearchConfig 接口维护。

---

## 7. Embedding 解析与检索

### 7.1 文档向量化

```text
Document
  → KnowledgeBase.embedding_model_id
  → Embedding Model
  → Document Vector
```

删除以下回退逻辑：

```text
KnowledgeBase 未配置 Embedding
  → 使用用户默认 Embedding
```

改造后，知识库缺少 `embedding_model_id` 应视为数据异常并终止向量化。

### 7.2 查询向量

```text
Query
  → KnowledgeBase.embedding_model_id
  → Query Vector
  → 仅检索同模型生成的 Document Vector
```

必须满足：

```text
Document Vector Model
= Query Vector Model
= KnowledgeBase.embedding_model_id
```

当前项目已有的 `document_vectors.embedding_model_id` 和按模型过滤向量记录的机制继续保留。

### 7.3 用户默认 Embedding

用户默认 Embedding 模型可以保留，但只用于：

- 创建知识库时由前端预选；
- 记忆向量等不属于知识库索引的独立场景。

用户修改默认 Embedding 不能影响已有知识库。

---

## 8. Embedding 模型配置保护

Embedding 配置被知识库引用后，禁止：

- 修改实际模型名称；
- 修改 Provider；
- 修改 `model_type`；
- 修改向量维度；
- 禁用；
- 删除。

建议默认禁止修改 Base URL。相同模型名称在不同服务地址后面不一定代表相同的模型版本、池化方式或归一化策略。

允许维护：

- API Key；
- Timeout；
- Retry Times。

长期建议将当前同时承担显示名称和上游模型标识的 `name` 拆成：

```text
display_name
model_name
```

模型引用保护应放在 ModelConfig Service 或统一业务层，不能只在 Controller 或前端实现。

## 9. 创建 Conversation

### 9.1 创建流程

```text
进入知识库问答页面
        ↓
选择 Chat 模型
        ↓
创建 Conversation
        ↓
保存 conversation.chat_model_id
```

### 9.2 创建接口

```http
POST /api/v1/knowledge-bases/:kb_id/conversations
```

请求：

```json
{
  "title": "新会话",
  "chat_model_id": "chat-config-id"
}
```

后端校验：

- KnowledgeBase 存在且属于当前用户；
- Chat 模型存在且属于当前用户；
- `model_type = chat`；
- `enabled = true`；
- 模型配置完整。

这些校验只保证 Conversation 创建当时模型有效，不能替代 Run 创建时的重新校验。

---

## 10. Conversation 切换 Chat 模型

建议新增专用接口：

```http
PATCH /api/v1/conversations/:conversation_id/chat-model
```

请求：

```json
{
  "chat_model_id": "new-chat-config-id"
}
```

后端重新校验模型归属、类型、状态和必要配置，然后只更新：

```text
conversation.chat_model_id
```

切换规则：

```text
Conversation 当前 = Qwen
        ↓ 创建 Run #1
Run #1 使用 Qwen
        ↓ Conversation 切换为 DeepSeek
Run #1 仍表示 Qwen
        ↓ 创建 Run #2
Run #2 使用 DeepSeek
```

Conversation 当前模型不可用时：

- 保留 Conversation；
- 禁止使用该模型创建新的 Run；
- 返回 `MODEL_UNAVAILABLE`；
- 引导用户切换其他 Chat 模型；
- 不自动回退到用户默认模型。

---

## 11. Agent Run 创建流程

客户端创建 Run 时不直接提交 `chat_model_id`：

```json
{
  "knowledge_base_id": "kb-id",
  "conversation_id": "conversation-id",
  "query": "用户问题"
}
```

Chat 模型由后端从 Conversation 读取，避免客户端提交与会话状态不一致的模型。

新的创建流程：

```text
用户发送问题
  → 查询并校验 Conversation
  → 校验 Conversation 与 KnowledgeBase 的关系
  → 读取 conversation.chat_model_id
  → 重新校验 Chat 模型
  → 创建 User Message
  → 创建 AgentRun
  → 写入 agent_run.chat_model_id
  → 投递异步任务
```

### 11.1 Run 创建时必须重新校验模型

Conversation 创建或切换时的模型校验只代表当时有效。创建 Run 时必须重新检查：

- 模型配置仍然存在；
- 模型仍属于当前用户；
- `model_type` 仍为 `chat`；
- 模型仍处于启用状态；
- 必要配置仍然完整。

不能只相信 Conversation 创建或切换时的历史校验结果。

### 11.2 并发一致性

建议在同一事务中：

```text
锁定 Conversation
  → 读取当前 chat_model_id
  → 重新校验模型
  → 创建 User Message
  → 创建 AgentRun 并保存模型引用
  → 写入 Outbox
  → 提交事务
```

Conversation 模型切换接口应使用兼容的事务或锁策略，使并发结果由提交顺序明确决定。

---

## 12. Worker 与 ContextBuilder

Worker 执行时只读取：

```text
AgentRun.chat_model_id
```

不得重新读取：

- 用户默认 Chat 模型；
- `KnowledgeBase.default_chat_model_id`；
- `AgentConfig.chat_model_id`；
- `Conversation.chat_model_id`。

原因是这些值可能在 Run 排队期间发生变化。

建议调整 `AgentContextRequest`：

```go
type AgentContextRequest struct {
    UserID          ID
    KnowledgeBaseID ID
    ConversationID  ID
    RunID           ID
    Query           string
    ChatModelID     ID
}
```

Worker 从已领取的 Run 填充 `ChatModelID`。ContextBuilder 继续从 AgentConfig 加载行为参数，但不再从 AgentConfig 决定 Chat 模型。

HTTP 创建 Run 阶段只做权限、Conversation、模型和基础配置校验；完整的会话上下文、记忆、检索和工具构建放在 Worker 阶段，避免重复构建并读取到不同状态。

---

## 13. 重试规则

重试应沿用原 Run 的模型身份引用：

```text
Run #100.chat_model_id = Qwen
Conversation 当前已切换为 DeepSeek
        ↓ 重试 Run #100
新重试 Run 仍使用 Qwen
```

因为重试表示重新执行原任务。

如果用户希望使用 Conversation 当前的新模型重新回答，应正常创建一个新 Run。

如果原模型已经不可用，应返回明确错误，不得静默切换到 Conversation 当前模型或用户默认模型。

---

## 14. Reranker 规则

Reranker 统一保存在：

```text
search_configs.reranker_model_id
```

允许：

- 动态更换；
- 清除关闭；
- 调用失败时降级为 RRF。

Reranker 只对候选 Chunk 实时评分，不改变已有文档向量，因此不需要知识库级不可变约束。

---

## 15. 前端调整

### 15.1 知识库创建页

- 增加必选的 Embedding 模型选择器；
- 展示“创建后不可修改”的提示；
- 不显示 Chat 模型；
- 没有可用 Embedding 模型时禁用创建；
- 提供前往模型配置的入口；
- 用户默认 Embedding 只用于预选。

### 15.2 知识库设置页

- 删除 Chat 模型选择器；
- Embedding 模型改为只读展示；
- 不再提交 Embedding 模型字段；
- Reranker 继续在检索设置中修改或关闭。

```text
向量模型

BAAI/bge-m3                         🔒
维度：1024

知识库创建后无法修改向量模型。
如需使用其他模型，请重新创建知识库。
```

### 15.3 Conversation 页面

- 新建 Conversation 时选择 Chat 模型；
- 输入框附近展示当前模型；
- 允许切换模型；
- 切换成功后提示“后续请求将使用该模型”；
- 不把 Conversation 当前模型显示成历史消息模型；
- 当前模型不可用时提示切换；
- 没有 Chat 模型时引导前往模型配置。

### 15.4 运行详情

运行详情中的 Chat 模型必须从：

```text
agent_runs.chat_model_id
```

读取，不能从 Conversation 当前模型读取。

如果只保存了模型配置 ID，页面应描述为“模型配置引用”或直接展示解析后的模型名称，不应声称保存了完整执行配置快照。

## 16. 模型配置生命周期

### 16.1 Embedding 模型

被知识库引用时：

- 禁止删除或禁用；
- 禁止修改模型身份字段；
- API Key 等连接凭据允许维护；
- Base URL 默认禁止修改，除非系统能够验证实际模型身份未变。

### 16.2 Chat 模型

- 创建 Conversation、切换 Conversation 和创建 Run 时都必须校验启用状态；
- 配置采用软删除，保留历史模型身份；
- 被 Conversation 当前引用时，禁用后应阻止创建新 Run；
- 被历史 Run 引用时不能物理删除身份信息。

### 16.3 Run 创建后模型被禁用

系统必须选择并固定一种策略：

1. 已创建的 Run 按模型引用继续执行；或
2. Worker 发现模型禁用后明确失败。

推荐采用第一种：禁用阻止创建新 Run，但不影响已经成功提交的 Run。无论采用哪种策略，都不得自动更换模型。

## 17. 数据库迁移方案

### 17.1 第一阶段：新增字段

先增加 nullable 字段：

```sql
ALTER TABLE knowledge_bases
ADD COLUMN embedding_model_id uuid;

ALTER TABLE conversations
ADD COLUMN chat_model_id uuid;

ALTER TABLE agent_runs
ADD COLUMN chat_model_id uuid;
```

先添加外键和必要索引，暂不设置 `NOT NULL`。

### 17.2 KnowledgeBase Embedding 回填优先级

历史迁移必须遵守：

> **实际向量记录优先于旧配置字段。**

建议优先级：

```text
1. 当前生效索引版本对应的 document_vectors.embedding_model_id
2. 当前有效文档记录中的 documents.embedding_model_id
3. knowledge_bases.default_embedding_model_id
4. 用户默认 Embedding，仅用于没有任何向量和有效索引的空知识库
```

具体规则：

- 优先检查知识库当前生效索引版本的实际向量记录；
- 实际向量记录反映已经持久化的真实向量空间，因此优先于旧配置字段；
- 如果当前生效索引存在多个 Embedding 模型 ID，禁止自动选择，应输出异常清单并人工处理；
- 如果没有向量，但文档记录保存了唯一的 `embedding_model_id`，使用文档记录；
- 只有没有实际索引证据时，才使用旧知识库配置字段；
- 用户默认 Embedding 只能用于完全没有向量历史的空知识库，不能用来推测已有索引使用的模型。

### 17.3 Conversation 回填

旧 Conversation 的 Chat 模型按以下顺序回填：

```text
1. agent_configs.chat_model_id
2. knowledge_bases.default_chat_model_id
3. 用户启用的默认 Chat 模型
```

无法安全回填的 Conversation 应记录迁移异常，不能随意选择任意模型。

### 17.4 AgentRun 回填

建议顺序：

```text
1. 原 Run 关联 AgentConfig 中的 chat_model_id
2. 能够根据消息 model_config_id 明确确定的实际模型
3. Conversation 回填后的 chat_model_id
```

这里回填的是模型身份引用，不代表还原了完整执行配置。

### 17.5 切换新字段

完成回填并验证后：

```text
knowledge_bases.embedding_model_id → NOT NULL
conversations.chat_model_id        → NOT NULL
agent_runs.chat_model_id            → NOT NULL
```

### 17.6 删除旧字段

确认新代码不再读取旧字段后，删除：

```text
knowledge_bases.default_embedding_model_id
knowledge_bases.default_chat_model_id
knowledge_bases.default_reranker_model_id
```

## 20. 验收标准

### 20.1 KnowledgeBase

- 没有 Chat 模型也可以创建知识库；
- 没有 Embedding 模型不能创建知识库；
- 创建时显式保存 `embedding_model_id`；
- 创建后前后端均不能修改或清空 Embedding；
- 文档索引和知识库检索不再回退用户默认 Embedding；
- 被引用的 Embedding 配置不能修改身份、禁用或删除。

### 20.2 Conversation

- 创建 Conversation 时必须选择可用 Chat 模型；
- Conversation 正确保存并返回 `chat_model_id`；
- 同一 Conversation 可以切换 Chat 模型；
- `chat_model_id` 明确定义为后续 Run 默认选择，不代表历史模型；
- 模型不可用时可以切换其他模型；
- 不自动回退用户默认 Chat 模型。

### 20.3 AgentRun

- 创建 Run 时重新校验 Conversation 当前模型；
- 创建 Run 时固化 `chat_model_id`；
- Worker 只使用 Run 中的模型身份引用；
- 已创建 Run 不受 Conversation 后续切换影响；
- 重试沿用原 Run 的模型身份引用；
- 不把单一模型 ID 描述为完整配置快照；
- Message 保存实际使用的模型 ID。

### 20.4 Reranker

- Reranker 只有 SearchConfig 一个权威数据源；
- 可以修改或关闭；
- 调用失败时降级到 RRF。

### 20.5 数据迁移

- Embedding 回填以实际向量记录为最高优先级；
- 多模型索引不会被自动选择或覆盖；
- 无法安全回填的数据会形成异常清单；
- 只有完成回填验证后才增加非空约束和删除旧字段。

## 21. 最终架构

```text
                         AIModelConfig
                              │
             ┌────────────────┼────────────────┐
             │                │                │
         Embedding           Chat          Reranker
             │                │                │
             ▼                ▼                ▼
      KnowledgeBase     Conversation      SearchConfig
             │                │
             │ 不可变         │ 后续 Run 默认选择，可切换
             │                ▼

             │                │ 模型身份引用不可变
             ▼                ▼
       DocumentVector      Message
```

最终必须明确：

```text
KnowledgeBase.embedding_model_id
→ 创建后不可修改

Conversation.chat_model_id
→ 后续 Run 默认选择，可以切换，不代表历史模型

AgentRun.chat_model_id

```

## 22. 最终定义

> 知识库创建时必须绑定一个 Embedding 模型。该模型决定知识库文档向量和查询向量所在的语义空间，因此属于不可变的索引级配置。历史数据迁移时，以当前生效索引中的实际向量记录为最高优先级，不能使用旧配置字段覆盖真实向量空间。
>
> Chat 模型不参与知识库索引构建，因此不作为创建知识库的前置条件。Conversation 创建时必须选择 Chat 模型，并允许在对话过程中切换。`Conversation.chat_model_id` 只表示后续 Run 默认选择的模型，不代表历史 Run 或历史消息使用的模型。
>
> 每次创建 Agent Run 时，系统必须重新校验 Conversation 当前选择的 Chat 模型，并将模型配置 ID 固化为本次 Run 的模型身份引用。Worker 后续只依据 Run 保存的引用执行。该字段不是完整配置快照；如需严格还原历史执行环境，应另外保存 Provider、模型名称和关键推理参数。
>
> Reranker 只参与实时检索结果重排，不改变已有向量索引，因此作为 SearchConfig 的运行时配置，可以动态修改、关闭或在调用失败时降级。
